Reporting Agent for Linux security design

How the DataReel Reporting Agent for Linux protects a fleet inventory: an RSA key per host, certificate registration and approval, signed uploads with timestamps and one-time nonces, TLS 1.2 or later with hybrid post-quantum key exchange, the two RHEL 8 packages and the crypto policy, the report server checks, the protections on the host, quantum computing and the limits.

The current copy is at https://datareel.com/linux_reporting_agent/security_design.php.

Release: 1.1.3, with the report server pages of the same release. Audience: security reviewers, administrators and anyone deciding whether to run the agent on their hosts or trust the reports it sends. The source code is published, so everything on this page can be checked against it; the design does not depend on keeping it secret. The documentation has the setup steps, and the RPMs are on the downloads page.

1. What the agent protects, and from whom

The agent is a systemd service for RHEL 8, 9 and 10 that collects a report about its host (release, kernel, hardware, IP addresses, usage, logged in users, SELinux, firewall and SSH settings, failed services, pending updates, installed packages and, after a scan, the Red Hat security advisories the host still needs) and sends it as a text report to a report server, a CIFS share or an SSH server. The goals are:

  • Only your hosts report: the report server keeps a report only from a host that has registered its own key and has been approved by an administrator, or by an enrollment token the site chose to use.
  • Reports cannot be changed or replayed: every upload is signed over the report's hash, the host's name, the time and a one-time value. A changed report, a report sent again later or a report signed by another host is refused.
  • One host cannot speak for another: a report is always saved under the name of the host that signed it, and a name stays bound to the first key that registered it.
  • No open ports: the service only makes outgoing connections. Nothing on the network connects to it, and the DataReel System Monitor (DRSM) reads the reports without ever connecting to an agent host.
  • Inventory kept private: on the host the report, the key and the agent state are readable only by root; on the network TLS keeps it private, with hybrid post-quantum key exchange where both ends support it; on the server the pages that show it need a login.

The agent does not protect against someone who is root on a host (they can make it send any report they like or copy its key), against an attacker who controls the report server, or against a site that runs the server over plain HTTP. It reports what the host tells it; it is an inventory, not an intrusion detection system.

3. The host's identity

  • The key: on its first run the agent makes a 3072-bit RSA key with OpenSSL and saves it as /var/lib/drra/agent_key.pem, mode 0600 in a folder of mode 0700, owned by root. The copy in memory is wiped after it is written. Unlike the Windows agent, which keeps a non-exportable key in the Windows key store, the Linux key is a file: root can copy it, and so can anyone who can read the host's disk or backups.
  • The certificate: a self-signed X.509 certificate for that key, subject CN=<host name> (the short host name, lower case) and O=DataReel Reporting Agent, a random 128-bit serial number, SHA-256 with RSA, valid for 20 years, saved as agent_cert.pem. It is not used for TLS: it only carries the public key to the server. On every run the agent checks that the saved certificate matches the key and the host name, and makes a new one if not.
  • The fingerprint: the SHA-256 of the DER public key (SubjectPublicKeyInfo), printed by drra fingerprint, written to drra.log and shown on admin.php, so an administrator can match the two before approving.
  • Random values (nonces, the certificate serial) come from OpenSSL's random generator (RAND_bytes); hashes are SHA-256.

4. Registration and approval

  • The agent registers before it sends anything over HTTPS. It posts its host name, a timestamp, a random 128-bit nonce, its certificate, the enrollment token (empty if none) and an RSA signature over register\n<host>\n<time>\n<nonce>\n<SHA-256 hex of the certificate>.
  • register.php refuses the request unless the host name matches ^[a-z0-9][a-z0-9_-]{0,62}$, the nonce is 32 hex digits, the time is within max_clock_skew_seconds (300 by default) of the server's clock, the certificate's CN is the host name, the signature verifies with the certificate's own key, and the nonce has not been used.
  • A host name that is already registered with a different key fingerprint is refused with key_mismatch; only an administrator can delete the old registration. A known host with the same key only gets its current state back.
  • Approval: a new host is saved as pending and waits for an administrator to approve it on admin.php. If the site sets an enrollment_token in server.ini and keeps auto_approve_with_token = 1, a host that sends the same token is approved at once; the token is compared in constant time (hash_equals), and a wrong token is refused with bad_token. A host that sends no token is registered as pending.
  • Revoke and delete: a revoked host stays listed and its uploads are refused. Deleting the registration lets the name register again, with any key.

5. Signed uploads

  • Each upload carries the host name, a timestamp, a new random 128-bit nonce, the report and an RSA PKCS#1 v1.5 SHA-256 signature over upload\n<host>\n<time>\n<nonce>\n<SHA-256 hex of the report>, followed by one \n<field> <SHA-256> line for each OpenSCAP HTML report sent with it. The server checks it with openssl_verify against the certificate saved at registration, never against anything in the request.
  • Replay protection: the nonce is recorded per host, under a file lock, and a nonce that was already used is refused with replay. Nonces are kept for twice the clock window, and older requests fail the time check anyway, so a captured request cannot be sent again.
  • Where it is saved: as <host>_linux_report_agent.txt for the host that signed, whatever file name was sent, written to a temporary name and renamed, so a reader never sees half a report.
  • Replies are a STATUS: line the agent acts on. When the server says not_registered, pending, revoked or key_mismatch, the agent clears its saved state and registers again on its next cycle, so it notices a revoke or a deleted registration without anyone touching the host.
  • Hook uploads (reports from other tools, sent with drra submit) go to hook.php with the same checks, signed over hook\n<host>\n<time>\n<nonce>\n<hook ID>\n<subject>\n<SHA-256 of the envelope>\n<SHA-256 of the payload>. The server also requires a manifest for that hook ID, a subject that is the signing host itself, an envelope that matches the request, the manifest's size limit and minimum interval.

6. Transport and delivery methods

  • HTTPS uses libcurl and OpenSSL. The server's certificate and host name are checked against the system trust store (/etc/pki/tls/certs/ca-bundle.crt) or ca_file for a private CA. The agent pins no certificate and never follows a redirect with a signed request. TLS 1.2 is the oldest version the agent uses, whatever the host's crypto policy allows (RHEL 8's LEGACY policy allows TLS 1.0). verify_peer=0 and use_https=0 are for test servers only: the signature still stops changed or forged reports, but the inventory can be read on the network.
  • Which OpenSSL: every release build needs OpenSSL 3.5 (the long term support release) or later, except the RHEL 8 linux_reporting_agent package, which is for FIPS mode:
    PackageOpenSSL and libcurlCiphers and key exchange groups
    RHEL 8 linux_reporting_agentRHEL 8's own openssl-libs 1.1.1 and libcurlThe system crypto policy (FIPS mode with the FIPS policy). No ML-KEM.
    RHEL 8 linux_reporting_agent-openssl35OpenSSL 3.5.9 and libcurl 8.23.0 built in (static); the system OpenSSL 1.1.1 is not usedThe system crypto policy, applied by the agent (below); groups: X25519MLKEM768 first, then the classical groups, or [https] tls_groups
    RHEL 9 and 10The system openssl-libs (3.5 or later, required by the RPM) and libcurlThe system crypto policy, or [https] tls_groups
    The two RHEL 8 packages conflict; the openssl35 package will not install on a host in FIPS mode (section 9), and a switch is dnf install --allowerasing. The RPM build fails unless each binary uses the OpenSSL it must (tools/check_openssl.sh), and drra selftest shows the build, the OpenSSL in use, the FIPS mode, the crypto policy and, with a URL, the TLS version, cipher and key exchange group of a connection. Each upload and registration writes that TLS line to drra.log.
  • The crypto policy in the openssl35 package: its own OpenSSL does not read RHEL 8's openssl.cnf, so the agent reads the policy's OpenSSL back-end, /etc/crypto-policies/back-ends/opensslcnf.config, and applies its CipherString, Ciphersuites, SignatureAlgorithms and TLS.MinProtocol/TLS.MaxProtocol to every connection with OpenSSL's SSL_CONF commands, the same commands the system OpenSSL takes from that file. A minimum below TLS 1.2 (LEGACY allows TLS 1.0) is raised to TLS 1.2; FUTURE's higher security level (3072-bit RSA and stronger signatures) applies as it does for the system OpenSSL. Groups: [https] tls_groups when set; otherwise the policy's groups with X25519MLKEM768 put first when the policy is not FIPS; RHEL 8's policies name no groups, so OpenSSL 3.5's own list is used, which offers X25519MLKEM768 first (with the FIPS policy: P-256, P-384 and P-521 only). A setting OpenSSL 3.5 does not take is listed by drra selftest and in the service log, not dropped silently.
  • Feeds: the OVAL feed (RHEL 8 and 9) comes from Red Hat over HTTPS, and the RHEL 10 CSAF/VEX index from the report server's vex_index.php over the same TLS settings. Neither is signed by the agent's protocol: their integrity rests on TLS and on the server.
  • CIFS share: smbclient with a share login in /etc/drra/cifs_credentials (mode 0600). The report is copied under a temporary name and renamed. These copies are not signed: who can write is decided by the share and folder permissions. SMB signing and encryption are Samba's and the file server's settings.
  • SCP: the host's OpenSSH scp in batch mode with /etc/drra/id_ed25519, IdentitiesOnly=yes, StrictHostKeyChecking=yes by default against /var/lib/drra/known_hosts, and a timeout. Not signed either: the SSH account decides who can write. The SSH key exchange is OpenSSH's own, not the agent's OpenSSL settings.
  • DRSM reads report files; it trusts whatever is in its reports folder. Give only the report server or the share write access to that folder.

7. On the Linux host

  • The service runs as root, needs no firewall rule and opens no port. The systemd unit makes /usr, /boot and /etc read only and home folders read only, gives the service a private /tmp, and sets NoNewPrivileges, kernel tunable, module and control group protection, at low CPU and I/O priority.
  • /etc/drra/drra.ini (with the enrollment token) is mode 0600, and the files the agent writes (the key, the certificate, the registration state, the reports, the scan results) are private to root.
  • Report hooks run only from root-owned files that are not group or world writable, and can run as another user. Members of the drra-upload group can queue hook uploads; nothing else is open to other users.
  • The RPM keeps /etc/drra and /var/lib/drra on upgrade, so a host keeps its key and does not need to be approved again.
  • Vulnerability scans run by hand (drra scan) unless the site turns them on. They read the rpm database and run oscap or dnf; they download feeds but install nothing.

8. On the report server

  • server.ini, the registrations, the nonces, the reports, the hook data and the admin password file live in DATA_DIR. install_server.sh puts it outside the web root, or, on shared hosting, inside it with a Require all denied .htaccess. The library pages (lra_lib.php, lra_auth.php, hook_lib.php) cannot be opened from the web.
  • Host names and hook IDs are checked against fixed patterns before they are used in a file name, so a request cannot reach another folder.
  • admin.php needs a login: Apache Basic authentication (with require_remote_user = 1, the default, the page refuses to run without it) or, with login = drsm, the DRSM dashboard login. Every change on admin.php needs a per-session CSRF token, and all output is HTML-escaped.
  • Files are written to a temporary name and renamed into place.
  • TLS on the report server, including whether it offers hybrid post-quantum key exchange, is the web server's configuration, not the agent's (section 12).

The agent is not a validated cryptographic module and makes no FIPS claim of its own. Its cryptography is done by OpenSSL and, on the server, by PHP's OpenSSL extension:

  • RHEL 8 linux_reporting_agent package: uses RHEL 8's own OpenSSL 1.1.1, which runs in FIPS mode when the host is in FIPS mode (drra selftest shows OpenSSL FIPS: on), under the host's FIPS crypto policy. Red Hat has had RHEL 8's OpenSSL module validated under FIPS 140; check the certificate that covers your minor release and package version on Red Hat's compliance pages or the NIST CMVP list.
  • RHEL 8 linux_reporting_agent-openssl35 package: its built-in OpenSSL 3.5.9 is not FIPS validated. Its %pre refuses to install it when /proc/sys/crypto/fips_enabled is 1, and if FIPS mode is turned on later it refuses to run: it logs why and exits with status 78, which systemd does not restart (RestartPreventExitStatus=78). Hosts in FIPS mode use the linux_reporting_agent package.
  • RHEL 9 and 10: use the system OpenSSL, which in FIPS mode uses Red Hat's FIPS provider. Whether the provider version on a given minor release has a CMVP certificate, or is still in process, is Red Hat's to state: check it before relying on FIPS mode.
  • RSA 3072 with SHA-256 signatures and SHA-256 hashes are approved algorithms in FIPS mode. Check your site's policy with your security office if your site needs FIPS 140-3.

10. What a report holds

A report names the host, its serial number, IP addresses, logged in users, every installed package and version, pending updates, SELinux, firewall and SSH settings, failed services and, after a scan, the security advisories and CVEs still to fix. Together the reports are a map of the fleet and its weak spots, so treat the reports folder like any other sensitive inventory: keep the pages that show it behind a login, keep backups private, and give DRSM and other readers access only to what they need. The agent sends no passwords and no file contents beyond what report hooks and hook uploads are set up to send.

11. Limits, stated plainly

  • Root on a host can make it send any report, and can copy its key to another machine. The signature proves which key sent a report and that it was not changed on the way, not that its contents are true.
  • The agent key is a file: a disk image, a backup or a cloned virtual machine template carries it. Remove /var/lib/drra/agent_*.pem from templates, and keep backups private.
  • The enrollment token is a shared secret. With auto-approval on, anyone who has it can register a host under an unused name. Use admin approval, or turn auto-approval off or change the token after a rollout, if that matters to you.
  • The first key to register a name wins. A host that registers before the real one holds that name until an administrator deletes it: check fingerprints before approving.
  • CIFS and SCP deliveries are not signed, and DRSM trusts its reports folder.
  • The SCP key has no passphrase. Limit the SSH account to the reports folder on the server.
  • Reports are saved on the server with mode 644. On a shared host, make sure other accounts cannot read DATA_DIR.
  • The replay check depends on the clocks: a server whose clock is far off refuses good reports (bad_timestamp), and the fix is the clock, not a larger window.
  • The RHEL 8 openssl35 package's OpenSSL and libcurl are built in: their security fixes come with new agent releases, not with dnf update openssl. The linux_reporting_agent packages get them from Red Hat.
  • The agent's own security updates come with new releases; it does not update itself.

12. Quantum computing

A large quantum computer, if one is built, could break RSA and elliptic-curve cryptography. For this agent that matters in two places:

  • Reports on the network: an attacker who records TLS traffic today could decrypt it later if the TLS key exchange was classical ("harvest now, decrypt later"). The reports are an inventory with the fixes each host is missing, so the key exchange is what decides how long they stay private.
  • Signatures: the RSA signatures could be forged once such a computer exists, which would let an attacker send false reports for a registered host. Signatures made today cannot be turned into anything readable later.

Hybrid post-quantum key exchange. Release 1.1.3 can use the hybrid TLS group X25519MLKEM768: ML-KEM-768 (NIST FIPS 203) combined with X25519, so the connection key stays secret as long as either of the two holds. The group is used only when both the agent and the report server offer it; otherwise TLS falls back to a classical group (X25519 or P-256) and the connection still works. What each build offers, as tested on 11/18/2026 against a server that offers the hybrid group:

BuildOffersKey exchange in the test

RHEL 9 and 10 hosts in FIPS mode follow Red Hat's FIPS provider and FIPS policy; check the group with drra selftest https://<your server>/ on such a host. The TLS: line in drra.log shows the group of every upload.

The report server decides too. A web server that does not offer the hybrid group gets a classical key exchange from every agent. For hybrid key exchange the server's TLS library needs ML-KEM (OpenSSL 3.5 or later) and a group list that includes it (for example Apache with SSLOpenSSLConfCmd Groups X25519MLKEM768:X25519:secp256r1, where supported). The datareel.com hosted report server does not offer the hybrid group yet, so connections to it use X25519 until the server supports ML-KEM; no agent change is needed when it does.

  • Quantum-resistant today: the TLS record encryption (AES-256-GCM, ChaCha20-Poly1305 or AES-128-GCM: the best known quantum attack roughly halves their key strength), SHA-256 (report hashes and fingerprints), the nonce and time checks, and the hybrid key exchange where both ends use it.
  • Not quantum-resistant: the RSA 3072 signatures and self-signed certificates, the report server's TLS certificate (RSA or elliptic-curve, from the public certificate authorities), classical TLS key exchange, and the SSH and SMB key exchange of SCP and CIFS delivery.
  • Standards, stated plainly: the agent is not CNSA 2.0 compliant. CNSA 2.0 calls for ML-KEM-1024 and ML-DSA signatures; this release uses ML-KEM-768 in a hybrid with X25519, which is the TLS hybrid group used by current browsers and servers, and RSA signatures. The RHEL 8 linux_reporting_agent package has no post-quantum algorithm, because RHEL 8's FIPS OpenSSL has none.
  • Moving on: a later release is planned to sign with ML-DSA (NIST FIPS 204) once PHP's OpenSSL extension on report servers can verify it, with a new registration for each host. RHEL 8's FIPS OpenSSL 1.1.1 will not get ML-DSA, so the RHEL 8 linux_reporting_agent package keeps RSA.

13. AI-assisted use

The AI-assisted guide (AGENTS.md) keeps an AI agent away from every secret on this page: it never reads the enrollment token, the agent's private key, a share login, an SCP key, server.ini or the admin passwords, never suggests copying the key, weakening a check, turning FIPS mode on or off or running the openssl35 package in FIPS mode, and never approves a host without the fingerprint check. People run or approve every step.

14. Reporting a security issue

Report security issues privately through the contact page, not in public issue trackers. Fixes go into the next release; the change log lists every release and what changed.
